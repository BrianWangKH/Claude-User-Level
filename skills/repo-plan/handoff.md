# Hand off and workers

Loaded by skill repo-plan (`cat ~/.claude/skills/repo-plan/handoff.md`) when a topic is settled and goes to a worktree. Follow it top to bottom.

## Hand off

1. Pick the branch `<type>/<scope>/<topic>` (global `CLAUDE.md`; kickoff uses `feature/docs/repo-init`) and run skill `new-worktree` with it.
2. Write the plan to the path it printed:
   - **all classes:** goal; class; in / out of scope; a `## Decisions` table `| Event | Choice | Reason | Decided by |` (older plans: `| 事件 | 選擇 | 理由 | 決定者 |`) with every decision, sub-decisions too (Decided by: user or planning; cite doc locations by heading, not section number); the source (link + quote) of every external fact the plan relies on, or "none"; empty `## Cost` and `## Friction` sections (new-worktree already copied the cost history into the worktree for the subagent estimates). `## Cost` starts with the header row `| agent | round | est usd | actual usd | est min | actual min | gap reason |`; the hooks record subagent rounds and worker runs, so it only gets the orchestrator's own rows and gap reasons.
   - **test-first, presentation, small fix:** also `## TODO items` (the TODO entries this topic covers, quoted as written in TODO); numbered rules with links to design sections; manual verification steps; empty `## QA commits` and `## Reviewer`.
   - **real-data checks:** the tests run on fixtures; what only the real data can show (the command runs, its output is deterministic, an error path refuses and writes nothing, a value stays in range) goes to `plans/verify/<topic>.json` **in the main checkout** (the worker can't write there), format in `~/.claude/templates/verify.json` (`cat` it): each check is a command plus what the hook can see (exit code, output text, files identical over two runs, files unchanged). `hooks/gates/verify.py` runs them after `STATUS: done` on a scratch copy of the real data, in the sandbox; in local mode auto-merge merges only when they pass, and run-result prints the result either way. Judgements a hook can't make (whether numbers make sense, whether a rule holds on real rows) go to the spec's `verifier` section (the template shows it): `usd` and `minutes` are the raw estimate for one verifier round, `judge` lists each judgement so it can be checked from the data. `hooks/gates/verifier.py` then runs a verifier agent after the checks pass: it reads the plan as the person approved it (copied when the person starts a run) and judges every rule of the plan plus the `judge` items on a copy of the real data. In local mode a failure of either layer goes back to the worker as a fix run by itself; only a check or verifier that can't run comes back to you. The plan's manual verification keeps only what needs a person (screens); UI checks go to `plans/manual-verify.md`. Run the spec's commands once from the planning session on the main branch before hand-off when they don't depend on the new code, so a typo in the spec doesn't fail the run.
   - **docs:** the files and sections to change and the intended content.
   - **investigation:** candidate options, how to test each, decision criteria, budget, and which doc gets the decision.
3. Delete the item from `Settled, waiting for a branch` (older: `已定案、待開 branch`) in `plans/repo-plan.md`.
4. Start the worker (below), or, if the user prefers, tell them to open a new desktop session in the worktree and send `/feature-flow <topic>`. You're free to plan the next topic.

## Queue (several settled topics, local mode)

When the user settles several topics in one session and wants them to run one after another without coming back between them, hand them off to the queue instead of `new-worktree` (local mode only; `hooks/worker/wt_queue.py` holds the rules):

1. For each topic write, in the main checkout, `plans/queue/<topic>.md`: the plan exactly as "Hand off" step 2 describes it, with the `## Worker mode` section, since the hook copies it into the worktree unchanged. Plus `plans/queue/<topic>.json`: `{"branch": "<type>/<scope>/<topic>", "order": <1, 2, ... the order to run them>, "after": [<topics it builds on>], "resources": [<repo tags>], "estimate": <the plans/worker/<topic>.json content that cost-history.py estimate printed>}`, and its `plans/verify/<topic>.json` when it has real-data checks.
2. `after`: every queued or in-progress topic whose merged result this plan relies on (code it calls, a decision it reads). A topic whose details depend on how an earlier one turns out isn't queued: it is planned after that one merges. Topics with no `after` between them still must not overlap in scope (Plan rules).
3. `resources`: tags the repo defines for things two runs mustn't use at once (an external API's quota, a shared data folder). Same tag, never together. None: `[]`.
4. Show the user the order, each `after` and `resources`, each estimate and the queue limits (the pane's line under the queue: each limit and its source; the smaller of `~/.claude/config/home.json` `budget` `queue_workers_max` / `queue_max_concurrent_usd` (or the person's `local.json`) and the repo's `.claude/flow.json` applies), then tell them to press `queue all` under Planned in `wt pane` (twice; it sends the topics in `order`), a topic's own `queue` button, or to type `wt queue <topic> <topic> ...`. Their press or prompt is the approval: never write the queue yourself, and never submit it for them.
5. The hook shows the person what started and why the others wait; it never enters this session (no model turn), so there is nothing to wait on here. Queued runs merge, finish and record their friction by themselves; `wt queue` and the pane show the queue, and the next planning session finds the results in `plans/friction.md` and the archive. If the user asks for progress, run `wt_queue.py status` (Bash, `python3 ~/.claude/hooks/worker/wt_queue.py status <main checkout>`) or `worker-status.py <topic>`.

Delete each topic from `Settled, waiting for a branch` (older: `已定案、待開 branch`) once it is queued.

## Worker (headless worktree session)

The worktree session can run headless with `claude -p`, so the user only talks to this planning session.

**Plan addition:** every worker plan gets a `## Worker mode` section (older plans: `## Worker 模式`, the same section): wherever the flow says to ask or tell the user and wait, the worker ends its run instead with a `STATUS:` line (the worker-stop hook enforces the format); it never guesses, never works around a block and never pushes (the push command goes in its next step). The last message is for the user, in the user's preferred language; commit messages and `PR_DESCRIPTION.md` stay in English.

**Estimate:** before the start, estimate the whole run's work in USD and minutes from the plan, without the quality gates' waits, and judge from the plan how many rounds the run will have of code-reviewer (each review or re-review round; a `Merge review:` runs no scan, leave it out) and of developer. Then run `python3 ~/.claude/skills/repo-plan/cost-history.py estimate branch <type>/<scope> <class> <usd> <minutes> --reviews <n> --dev-rounds <n>` (logic and wiring take both, small fix only `--dev-rounds`, other classes neither; the script says when one is missing or doesn't apply): it applies the estimate model (a fixed part plus a slope on the raw estimate, fitted to earlier topics of the same type/scope and class), adds the measured gate waits for those rounds (the mutation scan, crap-gate's coverage run; none in a repo with nothing to gate: no `.claude/quality-gates.json` and no tracked file of a language with a home profile) and prints the estimate, the limits and the `plans/worker/<topic>.json` content. No floors, no headroom of your own: the limits sit `budget_headroom_factor` above the estimate. Tell the user the raw estimate, the model (fixed part and slope), the gate waits and the result. A resume gets a new estimate for the rest of the work, with the rounds still to come.

**Start:** the sandbox has no `claude`, so the worker runs outside it.

- **With the worker-control hook** (`~/.claude/hooks/worker/worker-control.py` exists): Write `plans/worker/<topic>.json` in the main checkout before every launch and resume, with the content `estimate` printed: `{"minutes": <estimate minutes>, "est_usd": <estimate USD>, "raw_minutes": <raw minutes>, "raw_usd": <raw USD>, "hook_wait_minutes": <gate waits>, "class": "<class>"}` (the raw pair goes into each run's record, so the branch model compares actual, without the gate waits, with the raw estimate) (crap-gate checks only complexity for `presentation`) (add `"session_id"` only to adopt a session started by hand) (add `"flow": "scripted"` to run a logic, wiring or small-fix topic in the scripted flow, feature-flow `scripted.md`: the flow-next hook decides each step and the orchestrator only makes the calls; only when the user asked for it while it is on trial) (a merge run, skill `pr-conflict`: `estimate branch … --merge` adds `"mode": "merge"`, the start is `wt resume`, and the hook resumes the same session into `merge.md`, keeping the mode for later resumes). The hook records them per run (`.hook-only/runs/est-<n>.json`), sets `CLAUDE_WORKER_MINUTES` to minutes × `budget_headroom_factor` (the worker-budget hook stops the run there with `STATUS: blocked`) and passes est_usd × `budget_headroom_factor` as `--max-budget-usd`. Nothing goes into the plan's `## Cost`: run-result.py and `/finish-worktree` read the run files. When dispatch-guard stops a run only because the planned dispatch doesn't fit, the hook resumes it once by itself (worker-control.py auto; run-result.py says "Automatic resume: run <n> started" and the command to wait on it). Tell the user to type `wt launch <topic>` for the first run only; every later run of the same topic (after `needs-decision`, `blocked` or `wt stop`) is `wt resume <topic>` (launch refuses a topic that already has a session). `wt stop <topic>` stops it; `wt resume` also lifts an agent-guard hold in that worktree, so resume only after the user has decided on an ALERT. The hook starts the run in the background and adds the run number and the wait command to the prompt as context. Decisions go into the worktree plan while the worker is stopped; a resume always tells it to re-read the plan.
- **Auto mode and pane buttons** (wt-pane mod, `~/.claude/mods/wt-pane`): both only submit the same `wt launch|resume|stop <topic>` prompt, so the hook and the steps above stay as they are. With auto on (the user typed `wt auto on` or pressed `auto` in `wt pane`; this session only), the Write of `plans/worker/<topic>.json` comes back with a `wt-pane auto:` note: when it says the prompt is queued, give the estimate and end the turn without asking the user to type anything; the `wt` prompt then arrives by itself with the hook's `wt:` context, and **Wait** starts from there. When the note says nothing was started (an agent-guard HOLD, no worktree, already running), tell the user why and the command. With no note (auto off), tell the user the command as above, and that the pane's button does the same (press twice). Auto is the user's switch: never ask them to turn it on, and never write the estimate file only to set off a run they did not agree to.
- **Without the hook:** give the user the manual start command from `~/.claude/skills/repo-plan/worker-manual-start.md` (`cat` it), filled in.

**Wait:** right after the run starts, run in the background (`run_in_background`), so the harness notifies you when the run ends:

```bash
python3 ~/.claude/skills/repo-plan/run-result.py <topic> --wait
```

It reads the run's status (`hooks/lib/runstate.py`, the same one `wt status` and the pane show) every `status_wait_poll_seconds` and returns when the run has ended, may have died (`PHASE: orphan`) or can't be read (`PHASE: unknown`); never the worker's PID (invisible from the sandbox). Tell the user the run is going and that they can ask for "progress" (or the same request in the user's language) at any time.

**When it ends:** do what the script's `Next:` line says.
